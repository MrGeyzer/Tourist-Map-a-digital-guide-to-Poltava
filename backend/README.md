# Приймання звернень із сайту

Користувач заповнює форму й залишається на карті. Worker приймає POST `/report`, перевіряє поля та створює GitHub Issue від серверного облікового запису. Клієнту повертається лише номер звернення. Вхід у GitHub і переходи не потрібні відвідувачу. Адресат — команда репозиторію; автоматичного надсилання в міськраду/ОВА немає.

**Сервер поки не опублікований.** У `report-config.json` навмисно порожній `endpoint`. Без підключення Worker форма не повідомляє про успішне надсилання: залишає чернетку та пропонує її завантажити.

## Одноразове підключення власником

1. У GitHub увімкнути Issues для `MrGeyzer/Tourist-Map-a-digital-guide-to-Poltava`. Створити fine-grained access token лише для цього репозиторію з дозволом **Issues: Read and write**. Токен зберігати лише як secret Worker, не в HTML, `report-config.json`, Git чи чаті. Для сповіщень про нові звернення налаштувати Watch репозиторію у своєму GitHub.
2. У Cloudflare увійти у свій обліковий запис. Із папки `backend` через офіційний Wrangler:

```powershell
npx wrangler@4 login
npx wrangler@4 secret put GITHUB_TOKEN
npx wrangler@4 deploy
```

`secret put` запитає токен у терміналі; він не записується в код. Перевірити `backend/wrangler.toml`: `ALLOWED_ORIGINS` — точний origin сайту, без підпапки й кінцевого слеша. Для GitHub Pages це `https://mrgeyzer.github.io`. Після перенесення на власний домен додати його через кому. `namespace_id` обмежувача має бути унікальним для цієї програми у твоєму Cloudflare-акаунті; за потреби змінити `1001`.

3. Скопіювати адресу створеного Worker і в кореневому `report-config.json` задати:

```json
{"endpoint":"https://poltava-map-reports.YOUR-SUBDOMAIN.workers.dev/report"}
```

4. Запустити `npm run build` із кореня проєкту й опублікувати оновлений сайт, коли будеш готовий. Перевірити одну реальну заяву з позначкою «тест», переконатися, що вона з’явилася в Issues. Установлену PWA оновити через іконку офлайн-копії, щоб вона отримала новий endpoint. ZIP для цього не потрібен.

Усе до фактичного надсилання працює локально. Для локальної перевірки сервера можна використати `npx wrangler@4 dev` і origin локального сайту в `ALLOWED_ORIGINS`. Тестовий токен також зберігається в секреті або ігнорованому `.dev.vars`. Сервер і токен не входять у статичну папку `dist`.

## Поведінка й обмеження

- Неточність у даних, помилка сайту або інше; назва, необов’язкова назва/адреса об’єкта й опис. Координати користувача, контакти та IP у звернення не додаються. IP використовується лише обмежувачем частоти Cloudflare; це приблизне обмеження, спільна мережа може ділити ліміт.
- У браузері є перевірка полів, сервер незалежно перевіряє JSON та розмір запиту. CORS допускає лише налаштовані сайти; це не автентифікація від ботів. Додано приховане поле-пастку й ліміт 10 запитів за 60 секунд на IP у кожному регіоні Cloudflare. Для великого публічного навантаження можна додати Turnstile.
- Текст повідомлення зберігається як чернетка на пристрої при помилці або відсутності мережі. Автоматичного повторного надсилання немає. При розриві зв’язку після створення Issue відповідь може не дійти; повторна спроба може створити дубль.
- Звернення до публічного репозиторію публічні, про це написано у формі. Секрет і текст помилок GitHub клієнту не повертаються. Підтвердження успіху — лише HTTP 201 з номером реально створеного Issue.
- При зміні хостингу сайт лишається статичним; достатньо зберегти цей Worker або перенести той самий JSON-контракт на власний `/api/report`.

Документація: [секрети Cloudflare](https://developers.cloudflare.com/workers/configuration/secrets/), [обмежувач частоти](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/), [створення GitHub Issues через API](https://docs.github.com/en/rest/issues/issues#create-an-issue).
